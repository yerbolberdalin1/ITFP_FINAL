1. My work

I wrote DeliveryPipeline alone. I implemented the application code, tests, file handling and documentation. The console application calculates delivery prices, assigns orders to couriers, records completed deliveries and exports reports. I kept pricing and validation separate from console input and file operations. This let me test the rules with fixed inputs.

2. Models and validation

I made DeliveryOrder, Courier and Shipment immutable classes. Their properties only have getters, and their constructors are private. I used record types for values such as DeliveryQuote, PricedOrder and PricingRules. The declarations are in DeliveryOrder.cs:3–18, Courier.cs:3–18, Shipment.cs:9–29, Models.cs:10–15 and ReportModels.cs:3–16. This keeps an existing order or shipment from being changed after creation.

I used Create() methods to check input before constructing objects. DeliveryOrder.Create accepts distances above 0 and up to 500 km, and weights above 0 and up to 50 kg. It also checks IDs, destinations and delivery modes. It returns OrderResult.Valid or OrderResult.Invalid. Courier.Create checks capacity, range and speed. Shipment.Create checks cost, duration and timestamps. The checks are in DeliveryOrder.cs:21–40, Courier.cs:20–35 and Shipment.cs:32–46.

3. Error handling

I implemented Result<T> with Success and Failure cases. Map changes a successful value. Bind calls the next operation when the previous one succeeds. Both keep an earlier error and skip later work after a failure. I used these methods for expected failures such as missing orders and full couriers. The implementation is in Result.cs:3–55. Invalid API arguments can still throw exceptions.

I used Maybe<T> for lookups that may find nothing. Some holds a value, and None means it is missing. ToResult converts a missing lookup into a named error. I used this in FindCourier and FindShipment, so dispatch and completion can return a clear failure. The code is in Maybe.cs:23–35 and DeliveryWorkflow.cs:36–45.

4. Pricing rules

I wrote CreatePricing to return Func<DeliveryOrder, decimal>. I pass this delegate into workflows to change the pricing rule. The formula is base fee + distance × rate per km + weight × rate per kg. ModePricing uses a switch expression for Standard, Express and Priority. For 20 km and 5 kg, Standard gives 500 + 20 × 40 + 5 × 25 = 1425 KZT. The code is in Policies.cs:5–32.

5. Dispatch and delivery

I implemented Dispatch as a chain of lookups, validation, pricing, travel estimation and shipment creation. An order must exist, and its courier must exist. DispatchRules.Check runs before pricing or travel calculation. A failure returns through Bind without creating a shipment. The chain is in DeliveryWorkflow.cs:12–25.

I checked the shipment history to reject duplicate dispatch, including orders already delivered. I also checked the courier’s service range. For capacity, I collect that courier’s InTransit orders and add their weights. I reject the new order when its weight plus the active load exceeds capacity. Delivered shipments no longer use capacity. These rules are in DispatchRules.cs:8–25.

I implemented completion through DeliveryWorkflow.Complete and Shipment.Complete. A missing shipment returns SHIPMENT_NOT_FOUND. An InTransit shipment produces a new Delivered object. A delivery time earlier than dispatch is rejected. Repeating completion returns the same delivered object and keeps its first delivery time. I used a switch expression for this transition. The code is in DeliveryWorkflow.cs:28–33 and Shipment.cs:49–56.

For travel time, I wrote a calculation that depends on distance and speed. The native function rounds the result up to whole minutes. For 20 km at 40 km/h, the estimate is 30 minutes. NativeTravelTime checks the input and wraps the native call in Result<int>. It reports a missing library as a failure. The calculation is in native/deliverymath.c:3–14; the adapter is in NativeTravelTime.cs:14–49.

6. Repeated pricing in LINQ

I wrote ForVehicle to filter orders by capacity. I wrote ToPricedOrders with yield return, so it calculates each price only when the sequence is read. Creating the sequence does no pricing. Reading it again runs the pricing delegate again. The extension methods are in DeliveryExtensions.cs:5–24.

The difficulty was reusing this lazy sequence for several report queries. Calls such as Sum() and Count() enumerate the iterator and can repeat the price calculation. With two orders, one full pass makes two pricing calls. A second pass raises the total to four. I needed both reports to use the prices from the same calculation.

I fixed this by calling ToArray() before building the reports. ReportWorkflow.cs:50 contains the exact line below. It stores the priced items in memory. The workflow then adds travel estimates and passes the resulting items to Dispatch and TotalsByMode at lines 65–67.

var pricedOrders = orders.ForVehicle(capacity)
.ToPricedOrders(pricing).ToArray();

I verified the behaviour in DeferredExecutionTests.cs:8–59. The first test checks zero calls before iteration and one after the first MoveNext(). The second test reads the lazy sequence twice and checks four calls. The third creates an array, reads it twice and checks that the call count stays at two. I accepted storing the selected items in memory to avoid repeating their prices.

7. Saving shipment data

I implemented ShipmentsFile.Save to convert shipments into JSON data and call JsonFile.Save. It does this in ShipmentsFile.cs:61–67. In JsonFile.cs:45–48, I create a unique .tmp path beside the target, write the JSON there, and replace the target with File.Move(temporaryPath, fullPath, overwrite: true). The target is replaced after the temporary write finishes. This avoids writing partial JSON directly into the current shipment file.

I return FILE_WRITE_ERROR when saving fails and try to remove the temporary file. The error handling is in JsonFile.cs:51–67. This protects the target during an interrupted write, but the code does not force a disk flush or guarantee recovery after every power failure. On loading, I also reject unknown order or courier references, duplicate shipments and courier overloads in ShipmentsFile.cs:29–54.
